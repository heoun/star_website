# Star 后台：以租赁流程减少人工工作

日期：2026-09-08。依据：本地需求表（归档于 `notes/requirements/lease-information-2026-09-02.xlsx`，不提交 Git）、当前工作区实际代码、用户本轮确认及文末一手资料。本文为设计与实施建议，不代表这些功能已经上线；不改变当前数据库、权限或供应商配置。

## 本轮交付重点与外部设计文档对照

用户进一步明确：优先交付 Agent / Admin / Landlord 三种不同的查看与管理视角，以及可扩展的模块和契约。供应商 API 不作为这一轮视角与权限交付的前置条件。

已阅读用户提供的 [Star Leasing Platform: MVP Design（2026-09-03 草案）](https://claude.ai/code/artifact/0fd6714b-352e-4eaa-8af3-2ddc9c3610ab)，重点核对第 3 节权限、第 8 节架构/页面清单、第 9 节决定与假设。它是目标设计，不是当前 repo 的已实现清单；其中声称的历史决定仍需与用户本轮确认及现有代码区分。

| 草案中的内容 | 本轮处理 |
| --- | --- |
| 统一 policy、字段过滤、动作与状态联动 | 采用；实际 API 响应先过滤，写入和下载独立检查 |
| Case / Application / LeaseVersion 分离 | 保留方向；以增量关联接入现有申请和文件，不并行再造第三套数据 |
| Agent 默认 global，案件隔离到 Phase 3 | 修改：用户已明确仅负责人/协作者可访问，提升为本轮验收条件；按物业分配不能代替按案件隔离 |
| Admin/Agent 共用详细后台，房东门户在 Phase 2 | 调整：三种首页与详情视角本轮一同交付，共享业务组件，房东使用独立的摘要数据结构 |
| 负责 Agent 可直接维护所有物业默认条款 | 用户委托研究后决定。建议普通 Agent 编辑授权的本单条款、提出默认条款修改；Admin 发布物业默认条款。后续可给指定 Agent 单独授予指定物业的默认条款发布能力，案件负责人身份不自动授予该能力 |
| 房东查看收入、评分摘要和更多雇佣/历史信息 | 与“房东不参与申请审理”区分：收入/评分摘要可作为待确认的披露选项，不把更多历史资料默认开放；先提供内部通过后的出租条件摘要 |
| 新增角色只需插表 | 采用可配置授权的方向；新角色还需要权限映射、字段视图及验证，不能承诺任意角色零代码接入 |
| Preact / React、完整新目录及整库迁移 | 框架在草案中也未定；本轮保留运行中的后台入口和后端目录，先按职责拆组件，不把框架迁移设为权限改造前提 |
| 自动清理身份资料、删除旧表、不可回滚迁移 | 留作单独迁移工程，不能作为赶截止日期的顺手修改 |

### 本轮需要落地的最小结构

- 前端：一个共享应用外壳，AgentWorkspace、AdminWorkspace、LandlordWorkspace 三个角色入口；案件、房源、文件、租约组件按业务共享。角色切换仅用于隔离的演示环境，正式身份从服务端获得。
- contracts：明确 Principal / 资源关联信息 / Action / 字段规则 / 角色视图返回结构。案件关联必须区分负责人、协作者和所关联物业；沿用 backend/README.md 的契约评审流程。
- core：查询用例负责范围与字段投影，写入用例负责权限与状态前置条件，统一返回允许动作；页面不维护第二份业务权限。
- adapters：继续复用现有数据库、文件、身份与租约引擎。供应商模式分别表示未接入、人工核验或真实 API，不用模拟报告冒充真实结果。
- 数据：采用增量迁移，明确当前 public.applications 与 Case 的唯一关联；旧申请不会因迁移缺少证据而自动获得“房东已同意”状态。

### 三角色现场验收

准备 Admin、Agent A、Agent B、Landlord 四个独立测试账号和合成案例：Agent A 能审理自己负责或协作的案件，不能通过详情或文件 URL 访问 B 的案件；Admin 能分配和撤销协作、维护物业资料；Landlord 仅看自己物业已提交的出租推荐、记录出租决定、查看授权租约和提交修改请求。刷新后数据保留，撤销关联后访问失效。对于未接通的信用检查或电子签署，页面准确说明能力状态。

交付顺序：字段/动作矩阵和契约 → 服务端隔离及角色视图接口 → 三种工作台和必要管理动作 → 独立账号验收。后文关于完整自动化和供应商的阶段属于后续路线图，不全部压入周四版本。

### 物业条款权限：市场核对后的推荐决定

用户委托研究并推荐，不再将这个选择留作待用户回答的前置条件。以下是设计决定建议，尚未修改运行中的授权代码。

官方产品文档支持“角色能力与资源范围分别授权”，但不能据此声称所有平台都强制 Admin 审批物业默认条款：

- [DoorLoop 的权限配置](https://support.doorloop.com/en/articles/6380630-limit-access-to-your-users-by-editing-user-roles)分别配置 Rentals、Leasing、Reports、Settings；对象可区分查看列表、查看详情、新增、修改、删除，设置可只读或编辑。[用户配置](https://support.doorloop.com/en/articles/6106066-add-a-new-user-to-your-doorloop-account)另行限制物业或 Portfolio 范围。这支持将租赁处理和物业设置分开授权。
- [Buildium 添加员工](https://help.buildium.com/hc/s/article/How-do-I-add-staff-members-1557495009237)分别选择用户角色和可访问物业。[2016 年官方 Leasing Agent 介绍](https://www.buildium.com/blog/introducing-a-new-way-to-track-leasing-agent-commissions/)描述了租赁员工访问房源、申请及租约、隔离财务的设计思路；这是历史设计证据，不作为当前所有默认权限的保证。
- [Rentvine Pods](https://help.rentvine.com/pods-feature)按 Portfolio 集合限制物业、租约、报表和通知；其 FAQ 同时说明申请仍可全部可见，因此不能照搬成我们要求的案件隔离。
- [DoorLoop Owner Portal](https://support.doorloop.com/en/articles/8344889-customize-owner-portal-settings)单独配置房东报告、文件与请求入口，支持房东独立视角。它不能证明房东应该参与我们的申请审核。

据此结合当前七个 Agent 可编辑 lease 字段及用户业务流程，采用以下默认规则：

| 修改类别 | 推荐负责人和行为 | 理由 |
| --- | --- | --- |
| 本单租期、月租、押金、优惠等现有授权字段 | 负责/协作 Agent 可编辑本单草稿；不回写物业默认值。内部审批由 Agent 或 Admin 完成后，出租条件提交房东同意 | 让员工直接完成日常工作，避免每单重复要求 Admin 审批 |
| 物业长期默认条款、默认费用和租约模板 | Agent 或 Landlord 可提交一次结构化修改建议；Admin 看差异并发布新版本 | 这些数据会被后续多个案件继承，需要明确发布责任 |
| 房东法律主体、签署人关系、收款及内部财务配置 | Admin 维护；原始合同资料与资金配置单独控制，供应商密钥不返回浏览器 | 负责一个案件不等于可改变出租主体或收款对象 |
| 房源日常内容 | 公开资料共享查看；编辑按指定物业的独立维护权限授权，不从案件协作身份推导 | 公共内容维护和私密申请审理是不同职责 |

例如某单元默认月租为 3,000，Agent 为一个候选家庭填写 2,950：修改只属于该案件，房东确认本次 2,950；未来申请仍从 3,000 开始。如果房东希望今后都按 2,950 出租，提交物业默认值变更，Admin 发布后新案件继承新值。例子仅解释数据作用域，不替代当地金额或条款合法性校验。

为防止 Admin 成为瓶颈，修改请求包含旧值、新值、原因和影响范围，直接进入 Admin 待办，批准后自动落库，不要求 Admin 再抄写。普通本单编辑不产生额外 Admin 审批。批准绑定条款版本，关键条款后来变化则要求重新确认；默认条款更新不改写已批准或已签署版本。

扩展预留独立能力，例如 `property.defaults.publish`，并绑定授权物业。将来可以授予资深 Agent，无需把其升级为 Admin 或增加第四套界面。本轮只做明确的三角色预设与集中策略，不搭建复杂的通用权限编辑器。

## 1. 已确认的业务流程

租客浏览网站 → 选房 → 提交申请 → 支付申请费 → 第三方 credit check → 报告交给我们 → Agent 或 Admin 审核申请 → 内部通过后推给房东 → 房东同意出租 → 制作 lease → Tenant 先签 → Landlord 后签 → 全部签完结束。

- Landlord 不参与前面的申请审理，只确认团队推荐的出租安排，并签署租约。
- Agent 只能访问分配给自己或自己作为协作者参与的申请。公开房源资料可以共享。
- Agent 和 Admin 都能做内部审核，不增加每单都需要 Admin 再批一次的步骤。
- 内部通过、房东同意、全部签完是三个不同事实，不能共用一个含义模糊的 Approved。

## 3. 工作单位改成“一单租赁”

一单包含：房源/单元、主申请人和共同申请人、各自资料与检查状态、负责人/协作者、内部决定、房东确认、交易条款版本、租约版本、当前下一步和时间线。相同单元的不同候选家庭是不同案件；同住申请是同一案件的不同成员。

成员各自登录、上传和付款；成员不能看到彼此原始私密材料。共同租约需要的姓名和条款可出现在最终共享签署文件中。新增或退出签署人后，重新检查完整性和已批准的版本。

员工不再反复在申请列表、租约列表、修改请求之间找同一件事。首页任务直接打开案件中相关片段；完整资料、文档和历史按需展开。

### 状态与动作

| 业务阶段 | 谁需要做事 | 系统自动完成 | 人工动作 |
| --- | --- | --- | --- |
| 提交后待付款/补件 | Tenant | 返回下一步、供应商付款/授权入口、明确缺项、按规则提醒 | 租客完成自己的步骤 |
| 检查处理中 | 第三方 | 接收结果、匹配申请人、限次查询回补 | 超时/失败才交给负责人 |
| 待内部审核 | 负责 Agent 或 Admin | 资料与报告齐备后生成一个审核任务，集中展示待核验项 | 通过并提交房东 / 请求补件 / 不通过 |
| 待房东确认 | Landlord | 从本次已批准版本生成简短推荐包；按配置提醒 | 同意出租 / 提出调整 / 不同意出租 |
| 房东同意，准备租约 | Agent | 填入已确认物业资料、租客信息和交易条件，指出缺项与差异 | 检查最终版本，确认发给租客 |
| 等租客签署 | Tenant | 签署邀请、提醒、进度回执 | 租客签署；拒签/逾期才需要员工 |
| 等房东签署 | Landlord | 全部应签租客完成后开放房东签署 | 房东签署 |
| 已完成 | 无日常操作 | 验证签署完成、保存最终文件与签署凭证、更新案件/房源租赁状态 | 同单元冲突或归档失败时处理异常 |

付款、材料和信用检查进度应独立记录。页面只总结当前阻塞点，不能用一个 status 值丢掉其他事实。供应商不支持独立付款回执时，显示供应商可证实的进度，不能推断或要求员工伪造确认。

房东“提出调整”回到负责人处理；租金、租期、成员等关键条件变更后，旧确认不自动覆盖新版本。发签后修改需要作废旧信封并生成新版本，已经完成的签署文件不可被物业设置变化改写。

## 4. 三种角色的首页

首页只放“需要我处理”，等待付款/报告/签字的事项进入次级“系统跟进中”。正常等待不算逾期；只有超过规则阈值或出现失败才成为异常。处理完出现清晰空状态，不用统计卡填满页面。

| 角色 | 主要入口 | 首页内容 | 默认不展示 |
| --- | --- | --- | --- |
| Agent | 我的待办、我的租赁、房源 | 自己/协作案件的申请审核、房东调整、租约发签确认、跟进异常 | 全公司申请、系统配置、公司内部财务、几十项物业默认字段 |
| Admin | 待办与异常、全部租赁、物业与设置 | 自己承担的审核、无人负责案件、需要 Admin 修正的数据/条款、供应商失败 | 所有正常等待的事项堆成待办；每单的重复复核 |
| Landlord | 待我确认、我的物业、租约文件 | 团队已通过的出租推荐；租客签完后待自己签署的租约 | 申请审理队列、补件清单、信用报告、证件、银行流水、团队审核笔记 |

Admin 可以查看整体进度，但报表放二级入口。账号权限放设置里。房源修改请求放在具体物业/案件里，提交后进入正确负责人的待办，用户不需要再维护一个独立工单后台。

### 一张房东确认页应该有什么

- 单元、拟签署租客姓名、拟租期、月租、押金、优惠和需要房东同意的特殊条款。
- “Star 团队已完成内部审核”，负责人及推荐时间。
- 本次需要同意的条件，尤其是相对原条件的变更。
- 同意出租、提出调整、不同意出租。

房东不重复核验收入、联系前房东或判断信用报告。若业务后续确实要求额外信息，按明确用途逐项开放，不把整份申请顺手附上。

## 5. 权限必须分开看“谁能改”和“谁能看”

| 信息/动作 | Agent | Admin | Landlord |
| --- | --- | --- | --- |
| 已公开房源信息 | 可看；编辑沿用授权 | 管理 | 自己物业可看 |
| 申请、核验资料、credit 报告 | 负责/协作案件，审核需要时展开 | 授权业务范围内访问 | 默认不可访问 |
| 完整 SSN/护照号码 | 不开放，保持现有边界 | 按需揭示并记录用途/访问 | 不开放，末四位也不默认展示 |
| 申请人身份纠正 | 提交纠正请求 | 修改并保留原始提交记录 | 不开放 |
| 内部审核笔记 | 负责案件的团队笔记 | 可看；可另设 Admin 私密笔记 | 不开放 |
| 物业资料与租约默认条款 | 与案件有关的条款只读 | 编辑、确认、更新版本 | 自己物业中需要确认的资料/条款 |
| 本单交易条款 | 按现有字段白名单编辑；例外按业务规则处理 | 可编辑 | 看本次推荐并同意/提出调整 |
| 内部费用、利润、供应商密钥等 | 内部财务默认不开放 | 财务按职责开放；密钥由服务端保管 | 不开放公司内部信息 |
| 最终已签租约 | 负责/协作案件 | 可查看 | 自己作为出租方的租约 |
| 账号、分配、访问规则 | 无管理权限 | 管理 | 无管理权限 |

上表为下一版建议。除“Agent 案件范围”和“Landlord 不参与审理”已由用户确认外，新增字段可见性仍应落实为可审查的白名单。Admin-only 维护的字段不一定 Admin-only 可见：租约上会打印的房东名称、通知地址等，Agent 必须能核对。

权限判断组合：身份角色 + 案件关联/所属物业 + 字段类别 + 允许动作 + 当前阶段。房东属于某物业，不代表能看该物业尚未推荐的候选申请。页面隐藏之外，接口响应、文件下载、导出、搜索、通知内容都要使用相同边界；撤销协作后后续访问立即失效。

## 6. 自动化优先级

先把确定的规则做可靠，再增加辅助 AI。

1. 一次录入、多处使用：申请人维护自己的资料，Admin 维护物业事实，Agent 确认本单交易条件。物业事实不得从别的物业样例静默继承；保留当前 repo 的显式确认原则。
2. 自动分配：优先明确指定的负责人；无有效匹配才进 Admin 的未分配待办。协作成员须显式增加，不能因访问同一房源就获得全部申请权限。
3. 自动催办：只催当前阻塞方；材料补齐、撤回、拒绝、完成或人工暂停后停止；有频率上限、下次时间和人工接管入口。
4. 自动归集：每人申请和报告归入同一案件；发给房东的推荐包由已批准版本生成，不用员工复制整理 PDF。
5. 自动准备文书：复用现有 Word 引擎，默认只让 Agent 核对少量交易值、变更和缺项。保留发签前的一次确认，后续可根据实际返工率再评估减少此步骤。
6. 自动签署流转：全部租客完成 → 房东签署 → 最终归档；不让员工自己改成 lease_signed。

AI 适合辅助分类文件、提取带原文出处的候选值、提示内容不一致、起草补件文案；不自动覆盖身份或合同金额，不自动选择/拒绝租客，不把未经验证的提取结果视为事实。首版不依赖 AI 即可省去大量转发、催办和重复录入。

自动化执行必须持久化，处理重复回执时不重复发信/建检查订单/发租约；任务写入与业务动作保持一致，失败限次重试后才产生人工异常。旧版本回执不得推进新版本，执行时重新检查案件状态和收件人权限。供应商 API 与租约格式、签名位置要先做完整样本验证。

## 8. 按依赖顺序实施

### 第一阶段：把业务与数据边界做对

- 确定 Case 与现有 applications、文件、租约快照的关联和旧数据迁移方式，保留既有 ID/文件和原始提交。
- 新增案件负责人/协作者，服务端执行访问规则；房东只在内部通过并明确提交之后得到推荐包。
- 区分内部审核结果、房东决定、签署事实；动作代替任意状态下拉框。
- 将首页收敛成三种角色的任务视角。详细表单继续按需使用。

### 第二阶段：接通租客到房东的自动推进

- 复用 portal 清单；可靠绑定共同申请邀请、成员进度。
- 接真实 screening 供应商的申请费/授权入口和结果。优先沿用 repo 的供应商收款方向，不预先引入单独收款系统。
- 上线持久化催办、失败重试、去重及停止条件，再让系统发送自动提醒。
- 建立简明、版本绑定的房东同意页面。

### 第三阶段：完成租约闭环

- 将已有真实物业/单元条款接到 Case，复用缺项检查和 Word 生成。
- 接真实电子签署，租客全部完成后房东签，收最终文件与签署凭证。
- 校验同单元同租期冲突，再更新房源；其他候选案件由明确规则处理，不静默批量拒绝或发拒绝信。

backend/README.md 要求 contracts 先经过 Ocean review。实现前应把本方案需要的案件协作、检查进度、审批事实、通知任务与字段视图整理成独立 contract 变更，按已有评审流程推进。本文没有修改这些接口。

### 验收应证明省了哪些步骤

- Agent 不能通过换 ID、下载地址、搜索或导出读取他人案件。
- Landlord 在内部通过前不可发现候选申请，通过后也不能访问原始审核材料。
- Admin 无须重复批准普通 Agent 已有权限批准的申请。
- 上传补件后，相关提醒自动停止；重启服务后待办/提醒不丢失。
- 每单关键租约值只录入一次，修改能看到来源与影响，不影响已签文件。
- 重复付款/报告/签署回执不重复触发操作；房东无法先于全部租客签署。
- 阻塞项会指出原因、当前负责方和下一步，而非要求员工猜测状态。

上线前记录每单人工触点、手动催件次数、重复录入次数和返工原因，再比较改造后结果。当前没有实测基线，不承诺虚构的节省百分比。

## 9. 后续接入时再确定的事项

已确定的流程和权限不需要反复确认。真正影响供应商接入的剩余信息是：实际 credit check 服务商及收费方式、报告访问/API 权限、电子签署供应商、房东联系人的真实资料。字段级 Admin 私密信息范围、提醒频率和超时处理由具体配置与可审查白名单落实。

## 10. 2026-09-08 实施进度

用户确认开始修改后，已将角色工作台、案件负责人/协作者、服务端权限与房东独立字段视图落到现有 applications 数据源。新增契约为 `backend/contracts/workspace.ts`，业务规则、仓储适配器和组合根独立存放；旧状态下拉框已改为有前置条件的动作。

物业默认值仍只有 Admin 发布，Agent 编辑单次租约七个交易字段。房东/Agent 可提交结构化建议，Admin 审批后原子写入默认值和关闭请求。最终租约生成时保存版本，签署采用外部回执登记并限制租客先于房东；签完 PDF 在私有 R2 中归档。

这次实现的是第一阶段和第三阶段中的版本/顺序/归档骨架。多人申请归组、真实供应商、自动催办、房源冲突和自动下架还没有接通，不以本地模拟 smoke 作为这些功能的上线证明。
